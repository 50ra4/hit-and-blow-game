# issue-plan スキル

引数として渡された GitHub Issue 番号を起点に、コードベースを調査し **実装計画ファイル** を出力する。

## 使い方

```
/issue-plan <issue番号>
```

## 実行手順

### Step 1: Issue 情報の取得

以下のコマンドで Issue の詳細を取得する。

```bash
gh issue view <issue番号> --json number,title,body,labels,assignees,milestone,state
```

Issue の内容から以下を把握する：

- **目的**: Issue が解決しようとしている問題・ユーザーストーリー
- **受け入れ条件**: 完了の定義（Acceptance Criteria）
- **スコープ**: 影響を受ける機能・ページ・コンポーネント

### Step 2: コードベース調査

Issue の内容に基づき、影響を受ける既存コードを調査する。

- README.md を確認する
- 関連ファイル・コンポーネントを特定する
- 既存の実装パターン・依存関係を把握する
- 変更が必要なファイルをリストアップする

### Step 3: 実装計画の策定（Plan Mode）

`EnterPlanMode` を使い、計画を策定する。

計画は **必ず** `<PROJECT_ROOT>/.claude/plans/issue-<番号>-<概要>.md` にファイル出力する。

ファイルを出力しなければ次のステップに進んではならない。

#### 計画ファイルのフォーマット

```markdown
# Issue #<番号>: <タイトル>

## 概要

<Issue の目的・解決する問題を1〜2文で要約>

**意図（なぜ必要か）**: <Issue が生まれた背景・ユーザーへの価値>

**選択理由**: <技術的アプローチの選択理由・代替案との比較>

---

## 変更ファイル

| ファイル           | 変更内容   |
| ------------------ | ---------- |
| `path/to/file.tsx` | 変更の概要 |

---

## タスク

### Task 1: <タスク名>

#### 受け入れ条件

- [ ] 条件1
- [ ] 条件2

#### 実装詳細

<具体的な実装手順・コード例・注意事項>
Haiku 4.5 でも迷わず実装できるレベルの具体性で記述する。
変更箇所のファイルパス・行番号・変更前後のコードを明記する。

---

### Task 2: ...

---

## 受け入れ条件

- [ ] 全体の受け入れ条件1
- [ ] 全体の受け入れ条件2
- [ ] `pnpm type-check` が通る
- [ ] `pnpm lint` が通る

## 注意事項

- <スコープ外の事項や既知の制約>
```

#### 計画策定の注意点

- 不明点・矛盾点は、憶測ではなく随時確認する
- 計画ファイルには **意図**（なぜ必要か）と **選択理由** を **必ず** 記載する
- 実装詳細は **Haiku 4.5 でも実装可能な粒度** で書く（ファイルパス・変更箇所・コード例を明記）

#### モデル委譲

Issueの複雑さに応じて、計画策定を以下のモデルに委譲してよい：

- 複雑な計画（新規機能・複数コンポーネント連携）→ モデル `opus` の Agent
- 簡単な計画（定数変更・テキスト修正・既存パターン踏襲）→ モデル `sonnet` の Agent

### Step 4: 計画ファイルのコミット

出力した計画ファイルを **必ず** コミットする。コミットしなければ次のステップに進んではならない。

```
docs: [ISSUE <番号>] 実装計画を作成
```

### Step 5: ユーザー承認

`ExitPlanMode` でユーザーに計画を提示し、承認を得る。

## 注意事項

- 最初に最新の main ブランチから作業ブランチ（`feature/issue-<番号>-<概要>`）を作成する
- その他の作業ルール・コーディング規約は `.claude/rules/` を参照
